## Bausteine

| Baustein | Umsetzung |
|---|---|
| Eingang | `analytics_event_inbox`: je `(tenant_id, event_id)` genau eine Zeile (Inbox-Deduplikation; die Plattformtabelle `inbox` wird nicht benutzt, weil ihr Revisionsmodell einen Snapshotabruf beim Eigentümer voraussetzt, den Analytics nie auslöst). Nutzlast auf die Fachfelder je Ereignistyp reduziert (`Source.events`), unveränderlich (Trigger). Gleiche `event_id` mit anderem Inhalt: `REJECTED_PAYLOAD_MISMATCH`. |
| Quellen und Ereignisse | `ATTEMPT` (`booking.attempt_recorded`), `OFFER` (`booking.offer_created`), `BOOKING` (`booking.confirmed`, `booking.cancelled`), `DRIVER_EVENT` (`driver.event_recorded`: Ankunft, Einstieg, Ausstieg, No-Show mit Wartezeit und Regelstand, Klärfälle), `VEHICLE_STATE` (`fleet.vehicle_blocked`, `fleet.vehicle_block_lifted`, `fleet.release_issued`, `fleet.release_revoked`). Zahlungsereignisse folgen mit den Kennzahlen, die sie brauchen (WP-M4-46 ff.). |
| Fakten | `fact_attempt`, `fact_offer`, `fact_booking`, `fact_stop_event`, `fact_vehicle_state`: **reine Funktion der Menge der Eingangszeilen** (Ordnung Aggregatrevision, Ereigniszeit, `event_id`); je Ereignis wird der betroffene Fakt aus allen Zeilen neu abgeleitet. Damit sind Wiederholung, Verspätung und Unordnung ohne Einfluss, ohne Ankunftsreihenfolge zu speichern. Buchungszustand im Fakt (Vorrang): `NO_SHOW`, `COMPLETED`, `CANCELED`, `BOARDED`, `CONFIRMED`, `UNKNOWN`. |
| Datenstand | `dataset_watermark` je Quelle: `processed_until` (jüngste Ereigniszeit), `completeness` (`COMPLETE`/`INCOMPLETE`), `gap_count`, `event_count`, `updated_at`. Eine fehlende Revision eines Aggregats mit lückenloser Revisionsfolge (Versuch, Angebot, Fahrerereignis, Fahrzeugsperre und -freigabe) macht die Quelle `INCOMPLETE`; kommt sie später, wird sie `COMPLETE`. Die Buchung hat keine lückenlose Folge (Zwischenzustände werden nicht verbraucht) und kennt nur die Reihenfolgeunabhängigkeit. |
| Wiederaufbau | `FactBase.rebuild(tenant)`: eine Transaktion, Fakten und Datenstände löschen und aus `analytics_event_inbox` neu ableiten; liefert dieselben Zahlen. |
| Mandant | Verarbeitung mit Tenantkontext je Transaktion (`TenantTransactions`), RLS auf allen Tabellen. Ein Ereignis, dessen Empfänger oder Eigentümer nicht der Mandant des Workers ist, wird verworfen (`REJECTED_TENANT`), bevor etwas gespeichert wird. |
| Parallelität | Transaktionale Advisory-Sperren: zuerst `event_id`, dann der Fakt (Buchung bzw. Aggregat). Zwei Worker mit demselben Ereignis: eine Wirkung; verschiedene Ereignisse derselben Buchung laufen nacheinander und verlieren nichts. |
| Minimierung | Keine Fahrgast-Klartextdaten; Start und Ziel nur als vergröberte Werte des Versuchsereignisses (`coarse_origin`, `coarse_destination`). Ein mitgesendetes Namens-, Kontakt- oder Adressfeld wird verworfen. |
| Grenzen | Der Datenstand wird je Ereignis aus der Quelle neu berechnet (ein Gruppen- und Zählzugriff je Quelle); für sehr hohe Ereignisraten ist ein inkrementeller Zähler oder ein Stapellauf nachzurüsten (Betriebsverdrahtung). |
